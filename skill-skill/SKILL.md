# Skill Distiller

## 1. 定位与目标

这个 skill 只做一件事：从当前会话或用户显式提供的 transcript 中，识别已经稳定、可复用、边界清晰的一类任务工作流，并起草为 skill 草稿。它不替用户做最终判断，不跨会话读取历史，不把零散提示词误包装成 skill。

输出目标有三个：

1. 找出值得长期复用的规则。
2. 把个人偏好与通用方法拆开保存。
3. 为每条规则补上可追溯来源，便于确认、删改和后续合并。

三层价值必须同时存在：

1. 沉淀重复劳动：减少下一次同类任务重新输入规则的成本。
2. 规范 skill 创建：把识别、起草、确认、合并做成标准化流程。
3. 积累个人方法资产：把用户自己的工作习惯单独固化为可复用字段。

## 2. 适用场景

- 一个任务已经经过多轮纠偏，且输出约束趋于稳定。
- 用户多次修正结构、文风、输出格式、评审重点或步骤顺序。
- 用户明确表达“以后按这个来”“帮我保存这个流程”“下次直接调用”。
- 需要把已经存在的 skill 与当前新规则做增量合并。
- 用户愿意人工确认保留哪些规则、删除哪些临时信息。

典型用户包括：

- 高频使用大模型完成专业任务的人，例如产品经理、运营、咨询、程序员、学生。
- 已经有自己的工作方法，但不想反复手动配置的人。
- 团队中负责沉淀方法论和统一输出口径的人。

## 3. 不适用场景

- 只有 1 轮纠偏，尚不足以说明是可复用流程。
- 当前要求明显是一次性上下文，例如某个客户、某个截止日期、某个当周版本。
- 用户仍在快速试错，结构和约束还在大幅波动。
- 用户明确拒绝过类似建议，或表示不想被提醒。
- 用户只想收藏几句提示词，而不是沉淀完整工作流。
- 没有当前对话上下文、没有 transcript、也没有本地文件可供追溯。
- 需要跨会话读取历史聊天才能完成判断。

## 4. 输入要求

支持以下输入形式：

- 当前会话里已经可见的上下文。
- 用户显式提供的 Markdown transcript 文件。
- 仓库内的本地 skill 文件，用于对比和合并。

推荐的 transcript 结构：

```markdown
## 第1轮
### 用户
...
### 助手
...
```

也支持以 `用户:` / `助手:` 开头的行式对话，但结构化 transcript 更利于来源标注。

## 5. 候选skill识别信号

只有满足多数信号时，才值得进入蒸馏：

- 同类纠偏次数 `>= 2`。
- 输出约束在最近 `3` 轮内无重大变化。
- 个人偏好类规则 `>= 1`，例如文风、结构、禁用表达、审查顺序。
- 可迁移规则 `>= 3`，且不是只对本次对象成立。
- 疑似一次性特例占全部提取规则的比例 `< 0.35`。
- 用户在对话中出现明确沉淀意图，或任务已经进入收尾阶段。

反向信号：

- 最近两轮仍在推翻前两轮规则。
- 规则高度依赖“这次 / 本次 / 今天 / 某客户 / 某项目”。
- 提取出来的大多数内容只是素材事实，而不是工作方法。

提醒策略必须克制：

- 只有当任务接近收尾时，才允许在当前工作流中主动建议蒸馏。
- 不要把“主动建议”理解为后台弹窗；它只是当前会话里的一句建议。
- 建议文案保持固定：

> 我注意到这段对话形成了一套稳定的工作规则，是否需要帮你沉淀为可复用的 skill，下次直接调用？

## 6. 蒸馏流程

1. 收集输入
   只使用当前会话、用户粘贴的 transcript 和仓库内本地文件。
2. 切分轮次
   把 transcript 切成按轮次组织的用户 / 助手片段，保留轮次编号。
3. 抽取规则候选
   重点抽取重复纠偏、稳定输出要求、负面约束、步骤顺序和个人偏好。
4. 过滤一次性内容
   把明显依赖本次项目、日期、版本、客户、临时目标的内容先标为 `suspected_one_off_exceptions`。
5. 划分通用层与个人层
   通用层保存方法论、结构、检查项；个人层保存文风、禁用词、偏好顺序、口径。
6. 计算质量信号
   对重复性、稳定性、可迁移性、个人化程度和误提炼风险打分。
7. 生成候选草稿
   用模板渲染 skill 草稿，并在文末列出全部规则来源。
8. 等待用户确认
   任何规则在被写入最终 skill 前，都必须允许用户删除、修改或补充。

蒸馏范围选择必须支持以下粒度：

- 只提炼写作结构。
- 只提炼风格约束。
- 只提炼纠错规则。
- 只提炼行业背景与输入要求。
- 提炼完整流程。

如果用户没有指定范围，默认提炼完整流程，但仍要把临时信息放到 `suspected_one_off_exceptions`。

## 7. 个人层与通用层分离规则

判断原则：

- 如果一个规则属于同类任务普遍成立的方法、结构或检查项，归入通用层。
- 如果一个规则体现的是用户个人习惯、表述偏好、口径约束或风险容忍度，归入个人层。

具体示例：

- 通用层示例
  - “代码审查先看行为风险，再看代码风格。”
  - “竞品分析必须覆盖目标用户、定价、渠道、护城河和风险。”
- 个人层示例
  - “先给结论，再给证据，不要先铺背景。”
  - “禁用‘赋能’‘抓手’‘闭环’这类词。”
  - “提交信息统一用 `feat(scope): summary`。”

如果一条规则同时包含方法和偏好，拆成两条分别存储，不要混写。

## 8. 长期规则与临时特例区分规则

优先视为长期规则的信号：

- 同类要求在 `>= 2` 轮出现。
- 规则不依赖具体项目名、客户名、日期、版本号。
- 换一个相似任务后仍然成立。

优先视为临时特例的信号：

- 出现“这次 / 本次 / 这个客户 / 这版 / 今天先这样”。
- 明显只服务于某一份材料或某一个对象。
- 用户自己将其描述为“本次先这么处理”。

具体示例：

- 长期规则
  - “PRD 不写大段空洞背景，先写目标、用户、范围、验收。”
- 临时特例
  - “这次 PRD 先不写商业模式，因为老板只看交付范围。”

临时特例可以放入候选 JSON 的 `suspected_one_off_exceptions`，但未经用户确认不能并入最终 skill。

## 9. 用户确认流程

确认时必须让用户至少能完成以下动作：

- 保留被正确提取的规则。
- 删除误提取的临时信息。
- 修改表述不准确的规则。
- 补充系统漏掉但用户认为重要的规则。
- 选择这是个人 skill 还是团队 skill。
- 选择是否允许在相似任务中继续主动建议调用。

确认界面的目标不是让用户重写一遍 skill，而是只做最小决策。

默认确认话术：

> 我已经把这段对话中的稳定规则整理成候选 skill。请先确认要保留哪些规则、删除哪些本次特例，再决定是否创建。

## 10. 版本演进与合并规则

- 新候选与旧 skill 高度相似时，优先增量更新。
- 新候选如果引入另一类任务，应建议拆分为两个 skill。
- 新候选如果只是修正旧 skill 的个人偏好，可做小版本升级。
- 新候选如果新增了通用工作流步骤或结构化检查项，可做次版本升级。
- 旧 skill 长期不再使用时，可以归档，但不要直接删除来源信息。

触发模式只按 Codex 当前真实能力设计为三种：

1. 纯手动：用户明确要求蒸馏。
2. 当前工作流中的主动建议：当识别信号满足条件时，在当前会话中建议蒸馏。
3. 由已保存 skill 触发的后续复用：在未来相似任务中由 Codex 命中 description 后调用。

这里没有后台常驻监听，也没有跨会话自动扫描。

建议的版本语义：

- `v0.x`：仍在探索期，规则可能继续收敛。
- `v1.x`：结构稳定，可作为日常默认工作流。
- `v1.x+1`：新增兼容规则或修正个人偏好。

## 11. 解释来源标注规范

每条提取规则都必须至少对应一条来源记录，格式建议如下：

- `规则：先结论后论据`
  `来源：对话第4轮：用户说“把背景压缩到最后，先给结论和判断。”`

来源标注要求：

- 必须包含轮次编号。
- 必须尽量保留原句关键措辞。
- 如果一条规则来自多轮重复纠偏，可以列多条来源。
- 如果来源不足，宁可不收录，也不要臆造。

## 12. skill健康度跟踪建议

- 每次实际使用后，记录是否仍然需要大幅返工。
- 连续 3 次使用都要新增同一类补充规则时，说明 skill 还不稳定，应继续迭代。
- 连续 5 次使用都无需修改核心结构时，可以考虑升级版本。
- 如果 skill 长期只在一个项目里成立，说明它可能粒度不对，应拆分或归档。
- 定期用 `assets/eval_checklist.md` 做是/否复盘，淘汰已经失效的规则。

健康度建议关注以下指标：

- 是否减少了后续同类任务的修改次数。
- 是否缩短了任务完成时间。
- 是否提高了首轮输出可用率。
- 用户是否频繁关闭或绕过这个 skill。
- 是否长期不再使用，导致 skill 库负担上升。
