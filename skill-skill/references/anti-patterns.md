# anti-patterns

## 1. 不要把一次性上下文误当成长期规则

是什么：
把“这次只给老板看”“这版先不写风险”之类的限定条件写进长期 skill。

为什么不好：
这类规则离开当前任务就失效，会污染未来同类任务。

正确做法：
先放入 `suspected_one_off_exceptions`，只在用户确认后决定是否保留。

## 2. 不要把所有用户的纠正都沉淀为skill

是什么：
只要用户改过一句话，就机械地收进 skill。

为什么不好：
用户的很多纠正只是临场修正，不代表长期工作方法。

正确做法：
只沉淀重复出现、已经稳定、可迁移的规则。

## 3. 不要创建粒度过细的skill

是什么：
把“写标题的方法”“不要用感叹号”单独做成一个 skill。

为什么不好：
这会把 skill 退化成提示词收藏夹，无法形成完整工作流。

正确做法：
skill 的最小粒度应是一类完整任务，例如“PRD 写作工作流”或“Python 代码审查工作流”。

## 4. 不要未经过用户确认就写入最终skill

是什么：
系统直接宣布“已为你创建 skill”。

为什么不好：
蒸馏结果必然存在误提取风险，未经确认就固化会把错误长期保留。

正确做法：
只生成候选草稿，让用户先删改、补充、确认。

## 5. 不要把这个工具做成提示词收藏夹

是什么：
只保存零散句式、万能提示词或聊天片段。

为什么不好：
这些内容缺少输入要求、执行步骤、输出规范和边界说明，复用成本仍然很高。

正确做法：
始终围绕“任务输入 - 执行步骤 - 输出规范 - 负面约束”来组织 skill。

## 6. 不要过度泛化规则

是什么：
把“这次适合”的规则扩写成“所有任务都应该这样做”。

为什么不好：
过度泛化会让 skill 丧失边界，既不准确，也难以维护。

正确做法：
明确标注适用与不适用场景，必要时拆分 skill，而不是无限加例外。
